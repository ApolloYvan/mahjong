# 实施任务：模拟决策地基（阶段一）——规则引擎 / 对战平台 v2 / 模拟器校准 / 速度实测

## 0. 背景与目标（先读，所有取舍以此为准）

**项目目标**：在当前对战场景下拿到能拿的所有分。每次决策选"本局期望得分 + 连庄价值"最大的动作；
番型路线（平胡 / 爆头 / 七对 / 七对·爆头 / 财飘 / 杠开…）随每摸一张、打一张重新计算；对手的胡牌速度
计入我方胡牌概率（对手快就放弃大番转快胡，对手慢且牌好就冲大番）；阶段末改为最大化晋级概率。

**为什么要做这一轮**：上一版"统一账本"用几段手写近似公式（路线 DP + 固定对手 hazard + 查表）
拼出期望分，每段误差叠加且无法单独检验；判定又靠实战 5 房（约 400 局，得分标准误约 ±0.9 分/局），
噪声大于效应，结论不可靠。

**新路线（两阶段）**：
- **阶段一（本任务）**：建好地基并逐项验收——
  - 与服务端 100% 一致的规则引擎；
  - 直接驱动生产出牌逻辑的同牌对战平台；
  - 模拟器与真实日志的校准对比；
  - 纯 Python 模拟速度实测。
- **阶段二（下一份任务，本轮不做）**：蒙特卡洛模拟决策。每个候选动作在同一批"随机补全的隐藏牌局"上
  模拟打完本局，取平均得分（含连庄价值）；阶段末换成晋级概率。上线与否只看本轮做出的对战平台的得分差和置信区间。

本轮**不改变任何生产决策行为**。

## 3. 交付项与验收标准

### G1 规则引擎 `mj/sim/engine.py` —— 与服务端 100% 一致

**要做的**：一个可复制（`clone()`，供阶段二做模拟分支用）的整局状态机。

完整实现以下规则：
- 136 张牌，每家发 13 张，庄家先摸；只能自摸，不能点炮。
- 白板"白"是财神：
  - 可以替代任意牌；
  - 不能被吃、碰、杠；
  - 爆头时摸到白，可以选择胡，或弃白续飘（动作链 chain_count）。
- 吃：只有出牌者的下家能吃；每人最多两摊吃。碰和明杠优先于吃；碰、杠不受两摊吃限制。
- 杠：暗杠、明杠、补杠；杠后补牌；杠开 ×2。
  - 最后 20 张禁杠。
  - **补牌从哪一端取、流局在墙剩几张时触发，都必须从日志实证，不许沿用 `mj/arena.py` 的 `len(tiles)<=20 即流局` 假设。**
- 抓打圈：有人打出财神的那一圈，其余玩家只能打刚摸到的牌，且不能吃、碰、明杠；打财神者本人豁免。
- 番数计算：
  - 直接复用 `mj.rules.evaluate`，不重写。
  - 调用参数（`chain_count`、`piao`、`meld_groups`、`must_kaoxiang`、`gang_open`）与生产 `mj/bot.py::hu_result` 的口径一致。
  - 覆盖七对分支番、4 个白板 ×2、爆头 ×2、杠开 ×2、动作链 ×2^n。
- 胡牌不强制：摸牌后可以不胡。
- 结算：
  - 闲家自摸 fan：胡者 +10×fan，庄家 −8×fan，另一闲家 −1×fan；
  - 庄家自摸 fan：胡者 +24×fan，其余每家 −8×fan；
  - `multiplier` 字段照日志核对。
- 换庄：胡者坐庄；流局庄家连庄。每房 8 局。
- 合法动作集合由引擎自己判定（服务器不下发 allowed_actions）。

**回放核对工具** `tools/sim_replay_check.py`：
- 把真实日志（`models/events/*.json`，用 `merge_rounds` 合并 block）的起手牌和事件序列逐步喂给引擎，采用"强制动作"模式。
- 每一步检查：
  - 该动作在引擎中合法；
  - 引擎状态与日志一致（手牌张数、墙剩余、副露、抓打圈状态）。
- 局末核对 `round_ended` 的五项：winner、draw、fan、detail 集合、scores。
- 服务端代打（`timeout kind=discard`，配对规则见 `mining_common.mark_auto_discards`）照常作为动作回放，但统计时单独计数。
- 跳过 `truncated` 或无 `start_hands` 的局，并报告跳过数。

**验收标准**：
- 完整局上 winner、fan、scores、流局判定的**不一致数 = 0**。
- 若有不一致，逐条列出（文件、局号、事件序号、期望 vs 实际）并修到 0。
- 确属日志缺陷的，单列说明原因，总数 ≤ 完整局的 0.1%。
- 报告中写明从日志实证得到的规则事实：流局触发点、杠补牌来源、抓打圈的精确边界、续飘链计番。每条附样本数。
- 冒烟可以用少量文件跑；全量核对写成命令交给用户。

### G2 对战平台 v2 `tools/arena2.py` —— 直接驱动生产出牌逻辑

**要做的**：
1. **`mj/sim/snapshot.py`**：
   - 从引擎状态为指定座位构造生产快照：字段名与语义与线上 `/state` 快照一致，以 `mj/state.py::normalize` / `DecisionState` 和 `mj/bot.py` 实际读取的字段为准，逐字段核对。
   - 只暴露该座位可见的信息：自己的手牌、各家弃牌和副露、墙剩余、god/抓打圈、chain_count、piao、round_no、dealer 等。
   - 每个座位的动作一律调用生产 `mj.bot.choose_action(snapshot)`，覆盖三个阶段：`draw`、`response_peng`、`response_chi`。
   - 返回非法动作时计数、按服务端超时规则兜底，并在报告中列出。
   - 目标：非法动作数为 0。
2. **权重按座位覆盖**（唯一允许的生产改动，在 `mj/fit.py::load_weights`）：
   - 加一个默认关闭的覆盖钩子，例如模块级 `_OVERRIDE` 加上下文管理器 `weights_overlay(dict)`。
   - 生效时返回 `{**DEFAULT_WEIGHTS, **file_weights, **overlay}` 或指定的完整配置。
   - 未启用时行为逐字节不变。
   - 对战中每个座位决策前切换到该座位的配置。
   - 同时提供"冻结文件权重"选项：对战开始时读一次 `models/weights.json`，避免每次决策都读文件、避免用户中途改文件导致前后不一致。
   - 测试 `tests/test_weights_overlay.py` 证明两点：未启用时与原函数结果一致；启用后只影响上下文内的调用。
3. **同牌对打 + 轮座**：
   - 每个"牌组"由确定性种子生成一整房（8 局）的牌墙序列。
   - A、B 两个配置按平衡座位表各坐 2 席，然后镜像换座再打一遍，参照 `mj/arena.py` 的 `seat_pattern_for_batch` / `_mirror_pattern`。
   - 连庄、换庄按真实规则延续 8 局。
   - **注意**：一旦两边打法不同，后续牌局就会分叉；"同牌"只保证起始牌墙相同。
4. **输出**：
   - A−B 每局得分差的均值与 95% 置信区间，按牌组聚类，参照 `_mean_ci95`；
   - 每房第一名率之差；胜率、平均番、七对/爆头/财飘占比的对照；
   - 吞吐量：每核每小时局数。
   - 支持 `--a overlay.json --b overlay.json --sessions N --jobs K --seed S`；结果缓存可续跑；同一 seed 结果完全可复现。
5. 抓打圈、杠、续飘全部生效（引擎即 G1）。`RULE_COVERAGE` 式的能力声明写进报告，不许夸大。

**验收标准**：
- **A/A 检验**：两边都用当前 `models/weights.json` 配置，至少 2000 局。
  - 均值差的 95% 区间必须包含 0；
  - 并报告区间半宽（这就是这个平台的分辨率）。
- 非法动作 = 0；超时兜底 = 0（离线环境不应触发）。
- 报告写明：要达到 ±0.3 分/局、±0.5 分/局分辨率，分别需要多少局、在 10 核上要跑多久。
- 冒烟跑少量局；A/A 全量写成命令交给用户。

### G3 模拟器校准 + 差距分解

**G3a `tools/sim_calibrate.py`**：对比三组的同口径统计。
- **三组**：
  - 对战平台自对局（4 席都用当前配置）；
  - 真实日志中高手（`MASTERS`）；
  - 真实日志中我方（user_id）。
- **统计口径**：
  - 按摸牌序号的胡牌率曲线（hazard）与累计胡牌率，分庄/闲、分副露数；
  - 番数分布（1/2/4/8/16+）；
  - 七对、爆头、财飘、杠开占胡牌的比例；
  - 每局平均吃、碰、杠次数；
  - 流局率；平均局长。
- 每项给出 n 和 95% 置信区间。
- **目的**：量化"模拟中的对手（我们自己的 bot）"比真实高手慢多少、小多少。阶段二的对手模型要按高手数据校准，这张表就是标靶。
- 本项只要求表格准确，不设通过阈值。
- 自对局和真实日志的差异，要在报告里写出最可能的原因。

**G3b `tools/gap_decompose.py`**（差距分解）：用真实日志，在"同桌有高手"的房间里，把我方与高手的每局得分差拆成四项：
1. 胡牌率差 × 平均胡牌收入；
2. 胡牌时平均番数差（对应收入差）；
3. 被自摸时的支付差，分庄、闲；
4. 做庄局占比与连庄差。
- 另外按"起手牌好坏"分层（按起手离胡距离和财神数分档），分别给出上面的分解。这回答的是"烂牌拿不到的分"和"好牌没拿满的分"各有多少。
- 每项给出置信区间（按房间聚类的 bootstrap，可用 `mining_common.cluster_bootstrap_ci`）。
- 四项之和必须与总得分差对账一致（误差 <0.01 分/局）。

### G4 纯 Python 速度实测 `tools/sim_bench.py` + `mj/sim/fastcheck.py`

1. **`fastcheck.py`**：查表版的判胡与"离胡距离"。
   - 覆盖标准胡（含副露组数）、七对、爆头判定，以及标准/七对的向听或距离。
   - 按花色分解：每门 9 位计数作为 key，预计算或惰性缓存该门的面子/搭子分解，字牌单独处理，财神作为通配。
   - 表如需落盘，放 `models/` 下，并报告体积。
   - **正确性**：随机生成至少 100 万手（含 0–4 张财神、0–4 副露），与 `mj.rules.win_standard` / `seven_pairs` / `baotou` 和 `mj.shanten` 逐一对比，不一致数 = 0。
2. **快速推演策略**（阶段二模拟里各家"打完本局"用）：
   - 先做一个最简单的贪心版：优先降低离胡距离，平局时比较有效进张数，允许按路线（平胡/爆头/七对/七对·爆头）固定目标。
   - 吃碰按简单规则处理。
   - 只要求快，不要求强；强度在阶段二按 G3 标靶校准。
3. **测速场景**（每项报告每秒次数）：
   - 从真实中局状态（取 1000 个日志中的出牌决策点）出发：随机补全隐藏牌（对手手牌 + 牌墙），用快速策略把本局推演到结束，记录各家得分。
   - 至少三种运行条件：
     - M5 性能核单进程；
     - 用 `taskpolicy -c background` 强制到能效核的单进程（模拟较慢的赛方机器）；
     - 10 进程并行。
4. **输出**：
   - 在 1.5 秒出牌预算、0.3 秒吃碰预算下，每个候选动作能跑多少次推演（按 3 个候选计）；
   - 性能分析：热点函数前 10（`cProfile`）；
   - 如果能效核单进程在 1.5 秒内跑不到每候选 300 次，列出进一步的提速方案和预估收益，不要擅自引入第三方依赖。
5. **额外测一项**："对手回合空闲时间"可用的计算量。
   - 吃碰窗口固定走满 1 秒，我方两次摸牌之间至少有 3 个对手回合。
   - 用真实日志估计我方两次决策之间的平均间隔秒数，写进报告。
   - 这决定阶段二能不能在对手回合提前模拟。
